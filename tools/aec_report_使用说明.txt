================================================================================
第一部分  这个工具是做什么的
================================================================================

先说"回声消除(AEC)"是什么。想象你在用免提打电话：
  - 对方（远端）的声音从你的扬声器里放出来；
  - 这个声音又被你的麦克风录进去；
  - 如果不处理，它会被当成"你说的话"传回给对方 —— 对方就会听到自己
    的声音延迟一会儿又回来，这就是"回声"，非常难受。
"回声消除"就是一套算法，负责把麦克风录到的这部分"扬声器泄漏的回声"去掉，
只留下你真正说的话。SeekAudio AEC 就是这样一个算法库。

这个工具 aec_report.py 的作用：
  把算法在芯片(ESP32-S3)上跑出来的结果，自动整理成一份"体检报告"，
  用来回答三个问题：
    1) 跑得快不快、省不省芯片资源？（算力、内存）
    2) 回声去得干不干净？（回声抑制）
    3) 你自己说的话有没有被误伤、听起来自不自然？（近端保真、感知质量）
  并且把 SeekAudio 的方案和另一套业界常见方案(esp-sr)放在一起对比，
  一眼看出谁更好、好多少。

工具本身不上芯片跑，它读的是两类"考试成绩单"：
  - log.txt        —— 芯片运行时打印的日志（算力、内存、回声等设备端数据）
  - 一批 wav 音频  —— 算法处理前后的声音文件，工具在电脑上离线重新分析
最后生成一份文字报告，同时显示在屏幕上、并保存成 aec_report.txt。

第二部分  快速上手（三种用法）
================================================================================

【需要准备的文件】把下面这些放到同一个文件夹里：
    log.txt        芯片日志（必需）
    near.wav       麦克风录到的声音（近端）
    far.wav        对方的声音 / 扬声器参考（远端）
    a1.wav a2.wav b1.wav b2.wav   四个配置各自处理后的输出声音
    Run_*Stage_0.onnx   （可选）AECMOS 打分模型，缺了就跳过那一节

【运行环境】电脑上装好 Python 3，然后按需安装依赖：
    pip install numpy librosa onnxruntime
  说明：
    - 只有 log.txt、没装库也能跑，会输出"设备端算力/内存"等；
    - 装了 numpy 且有 wav，才能自动识别场景、算回声/保真指标；
    - 想要 AECMOS 感知打分，还需要 librosa、onnxruntime 和那个 .onnx 模型。

--------------------------------------------------------------------------------
【用法一】最简单：什么参数都不加（自动检测，最省事；但不一定最准）
--------------------------------------------------------------------------------
    python aec_report.py

  工具会自动完成一切，包括"哪段是回声、哪段是你说话、哪段是双方同时说"
  ——这个由它从 near/far 声音里自动判断（详见第四部分）。判断结果会打印
  在报告开头，方便你核对。

  注意：自动判断对结构规整的素材通常没问题，但遇到带混响、远端语音有停顿
  的素材时，可能把"纯回声段"切碎或误判成双讲，导致回声指标不够准。所以
  ——**要得到最准的结果，请用下面的【用法二】手动指定场景段**。自动检测
  更适合当"快速查看"或对手动结果做交叉验证。

--------------------------------------------------------------------------------
【用法二】手动告诉它"哪段是什么"（★推荐：结果最准）
--------------------------------------------------------------------------------
  这是推荐的用法。只要你知道素材的确切结构（比如是自己录制/设计的），就直接
  指定时间段——它覆盖自动判断，结果最贴合真值、也最稳定：
    python aec_report.py --echo 0:10 --near 10:26 --dt 26:36

  三个参数分别是：
    --echo   远端单讲段（只有对方在说，纯回声）  例：0:10  表示第0到10秒
    --near   近端单讲段（只有你在说，没回声）    例：10:26
    --dt     双讲段（双方同时说）              例：26:36

  时间段格式规则：
    - 写法是 "起:止"，单位是秒，例如 0:10 表示第 0 秒到第 10 秒；
    - 一类可以有多段，用逗号隔开，例如 --echo 0:8,30:36；
    - 结尾用 -1 表示"一直到文件结束"，例如 --dt 26:-1；
    - 支持"只指定一部分"：只写 --dt，其余 echo/near 仍走自动判断。
    - 整段只有一种场景（全程纯回声 / 全程双讲 / 全程近端）时：只写那一类，
      再加 --no-auto 关掉对其余两类的自动检测（否则它会在单一场景素材上
      误检出不存在的段，结果就不准了）：
        全程纯回声  python aec_report.py --echo 0:11.22 --no-auto
        全程双讲    python aec_report.py --dt 0:36 --no-auto
        全程近端    python aec_report.py --near 0:36 --no-auto
    - 也可以把某一类显式写成 none 表示"这段素材里没有这种场景"，例如
      只有回声和双讲、没有近端单讲：
        python aec_report.py --echo 0:8 --near none --dt 8:11
      （三类都写全了，就不需要再加 --no-auto。）

--------------------------------------------------------------------------------
【用法三】结果文件不在脚本目录：用 --dir 指路
--------------------------------------------------------------------------------
    python aec_report.py --dir D:\out
    python aec_report.py --dir D:\out --echo 0:8,30:36 --dt 26:-1

  提示：随时可以运行 `python aec_report.py --help` 查看完整参数说明。

第三部分  先认识：四个被测配置 A1 / A2 / B1 / B2
================================================================================

报告里反复出现 A1/A2/B1/B2，它们是四种"回声消除+降噪"的组合方案。A 系
是 SeekAudio 自己的方案，B 系是业界常见的 esp-sr 方案，用来做对比。四者
用的是同一个"回声消除前端"，只是后面接的"降噪"不同，所以能公平比较：

    A1 = SeekAudio 方案 + 传统降噪(WebRTC NS)     —— SeekAudio 的"标准档"
    A2 = SeekAudio 方案 + AI 降噪                 —— SeekAudio 的"AI 档"
    B1 = esp-sr 方案   + 传统降噪(ns_pro)         —— 对手的"标准档"
    B2 = esp-sr 方案   + AI 降噪(NSNet2)          —— 对手的"AI 档"

对比是"同档比同档"：
    A1 对 B1（传统 对 传统）
    A2 对 B2（AI   对 AI）

一句话记忆：A 是"我们的"，B 是"对手的"；数字 1 是传统降噪，2 是 AI 降噪。

第四部分  先认识：三种"说话场景"（回声 / 近端 / 双讲）
================================================================================

评价一个回声消除算法，必须分场景看，因为不同场景要求不一样：

  ● 远端单讲（也叫"纯回声段"）：只有对方在说，你不说。
      这时你的麦克风里理论上只有"回声"。考的是：回声去得干不干净。
      —— 这是评价"消回声能力"最纯粹的场景。

  ● 近端单讲：只有你在说，对方不说。
      这时没有回声。考的是：你的声音有没有被误删、听起来自不自然。
      —— 这是评价"会不会误伤你说话"的场景。

  ● 双讲：双方同时说。
      这时麦克风里既有回声、又有你的话，两者混在一起。这是最难的场景，
      算法既要去回声、又不能把你的话也一起删掉。

为什么要区分？举个例子：在双讲时，好的算法会"手下留情"、保住你的声音，
代价是回声去得没那么彻底。所以如果不分场景、把双讲混进去算"消回声能力"，
数字会被拉低，**冤枉了算法**。工具区分场景，就是为了各算各的、不冤枉、
也不夸大。

工具怎么知道哪段是哪个场景？
  - 手动（用法二）：你直接告诉它时间段，最准；
  - 自动（用法一）：它从 far/near 声音里推断——对方在放音=可能有回声；
    对方没放音、你在说=近端单讲；对方在放音、但你的麦克风信号里还有一份
    "和对方声音无关的成分"=双讲。判断结果会打印出来供你核对，如果和实际
    不符，用 --echo/--near/--dt 手动修正即可。

第五部分  报告逐节详解 —— 每个指标到底是什么意思
================================================================================

在开始前，先解释几个反复出现的"单位/概念"，看懂它们，报告就通了：

  ★ dB（分贝）：一种"倍数"的表示法，用来说"强多少倍/弱多少倍"。
      对能量而言：10 dB ≈ 10 倍，20 dB ≈ 100 倍，30 dB ≈ 1000 倍。
      所以"回声被削弱 20 dB"= 回声能量被削到原来的百分之一。数越大越强。

  ★ dBFS：声音"绝对音量"的刻度。0 dBFS 是数字系统能表示的最大声，
      往下都是负数，越负越安静（-20 比 -10 小声，-60 已经很安静了）。

  ★ 帧：算法不是一个采样点一个采样点处理，而是攒一小段一起处理。
      本工具里一帧 = 32 毫秒（毫秒=千分之一秒）。36.74 秒约 1148 帧。

  ★ p95（95 分位）：把所有帧按耗时排序，第 95% 位置的那个值。
      通俗说："95% 的帧都比这个快，只有最慢的 5% 超过它"。它比"最大值"
      更能代表"常态下的偏慢情况"，不会被个别极端帧带偏。

--------------------------------------------------------------------------------
一、设备端算力  —— 跑得快不快、占用芯片多少
--------------------------------------------------------------------------------
这一节的数据来自芯片日志，反映"实时性能"。芯片主频 240 MHz。

  ● CPU avg / p95 / max（平均 / 95分位 / 最高 占用率，%）
      芯片被这个算法占用了多少。三个数分别是：平均情况、偏忙情况(p95)、
      最忙的那一帧。越低越好——越低说明越省芯片、越有余力干别的事。

  ● 等效 MHz
      把"占用率"换算成"相当于用掉了多少主频"。例如 240 MHz 的芯片占用
      26% ≈ 63 MHz。越低越省。

  ● RTF（实时倍率）
      "算得比实时快多少倍"。RTF = 3.78x 意思是：处理 1 秒的声音只花了
      约 1/3.78 秒。必须 > 1 才能实时（否则声音会越处理越卡）。越大越好，
      余量越足。

  ● 单帧 avg / p95 / max（每帧耗时，微秒 us；1 微秒=百万分之一秒）
      每处理一帧(32毫秒的声音)实际花了多少时间。因为一帧的"时间预算"是
      32000 微秒(=32毫秒)，只要每帧都在预算内算完，就不会卡。越低越好。

  ● 最忙帧#
      最慢的那一帧是第几帧。如果是很靠前的帧（如 #0~#10），通常是"刚启动
      热身"，属正常；如果在中间冒出个别慢帧，才需要留意。

  ● "破帧率"（注释里那句话）
      有没有哪一帧超过 32000 微秒的预算算不完。报告里四个配置的单帧最大值
      都远小于预算，所以"破帧率 = 0"，意思是全程稳、一帧都没超时。

--------------------------------------------------------------------------------
二、内存占用  —— 占多少芯片内存
--------------------------------------------------------------------------------
芯片有两种内存：片内 SRAM（快、但很少、很宝贵）和 PSRAM（多、但慢）。
省片内 SRAM 尤其重要。数字越低越好。

  ● 片内 SRAM create / +峰值
      "create"是算法初始化时占的片内内存；"+峰值"是运行过程中额外冲高的
      峰值。两者相加才是运行时真正的片内占用高点。

  ● PSRAM create / +峰值
      同上，但针对 PSRAM（较慢的大内存）。

  ● RAM 合计
      片内 SRAM + PSRAM 的初始化占用之和，一个总量参考。

  ● flash 模型
      有些方案（如 B2 的 AI 降噪 NSNet2）还需要把"模型权重文件"烧进 flash
      芯片，额外占 flash 空间（B2 需要约 1024 KB）。A 系不需要外部模型文件，
      这一栏是"-"。对比总占用时，这块要算进去（片内+PSRAM+flash）。

  ● 栈余量
      运行时"调用栈"还剩多少空间。这是安全余量，越大越安全（太小有溢出
      崩溃风险）。

--------------------------------------------------------------------------------
三、回声抑制  —— 回声去得干不干净（核心指标）
--------------------------------------------------------------------------------
这一节回答"消回声能力"。这里有一个最关键的指标：ERLE。

  ● ERLE（回声抑制量，dB）——最重要的消回声指标
      全称是"回声返回损耗增强"。别被名字吓到，通俗说就是：
      **回声被削弱了多少倍，用 dB 表示，越大越好。**
      比如 ERLE = 24 dB，意思是回声能量被削到原来的约 1/250。
      经验参考：10 dB 已经有效，20 dB 明显，30 dB 以上很干净。

    本节把 ERLE 分成两个层次给你看：

    [主口径] 离线场景感知 ERLE（工具在电脑上，按场景段重新算的，更准）
       - 远单讲 ERLE：在"纯回声段"上算的 ERLE。这是评价消回声能力最干净、
         最该看的数（因为排除了双讲干扰）。越大越好。
       - 残余回声(dBFS)：处理后剩下的回声有多小声（绝对音量）。越负越好，
         说明回声被压得越安静。
       - 双讲 ERLE：双讲段上的 ERLE。它天生偏低，因为双讲时算法要保住你的
         声音、不敢把回声压太狠——**这个数低是"设计如此"，不是缺陷**。

    [交叉参考] 设备端日志 ERLE（芯片自己算的，用来互相印证）
       - 芯片端算 ERLE 时分不清哪段是双讲，所以它的"回声活跃/收敛 ERLE"
         把双讲也混进去了，会被你的说话声拉低，数值偏保守。它们只作参考、
         和主口径对照，不作为最终结论。
       - "远单讲 ERLE(桶)"是芯片按时间分段(每2秒)统计里、开头纯回声那几段
         的平均，若素材开头恰好是纯回声，这个数就和主口径可比。

  ● 回声输入电平（近端 mic，远端单讲段，dBFS）
      处理"之前"，麦克风里回声本来有多大声。它是个基准：残余回声比它小
      多少，就对应削弱了多少 dB。

  小结：看消回声，主要看 [主口径] 里的"远单讲 ERLE"（越大越好）和
        "残余回声"（越负越好）。双讲 ERLE 偏低属正常。

--------------------------------------------------------------------------------
四、近端保真  —— 你自己说的话，有没有被误伤
--------------------------------------------------------------------------------
消回声不能"用力过猛"把你的声音也削掉。这一节衡量"你的声音保得好不好"。

  ● 链路延时（样 / 毫秒）
      声音从进算法到出算法，被延后了多久（样=采样点，毫秒是时间）。延时越
      小越好（太大会让通话感觉"慢半拍"）。报告还给出"延时地板"——四个配置
      共享的最小延时，以及各自比地板多出的额外延时。

  ● 近单讲相关（0~1）
      在"只有你说话"时，处理后的声音和你原始声音有多"像"。1 = 完全一样、
      毫发无损；越接近 1 越好，说明算法很"透明"、没误伤你的声音。0.99 这种
      就非常好。

  ● 双讲相关（0~1）
      双讲时处理后和原麦克风信号的相似度。**注意：这个数偏低是正常的**，
      因为双讲时算法故意去掉了回声，输出本来就该和"回声+你的话"的原始麦克风
      不一样。所以它是个"歧义指标"，不能简单地越高越好。双讲时的近端保真，
      更应该看下面第五节的 AECMOS "双讲 Other" 分。

--------------------------------------------------------------------------------
五、AECMOS 感知质量  —— 用 AI 模型模拟"人耳打分"
--------------------------------------------------------------------------------
（需要 .onnx 模型文件，缺了会显示"跳过"。）
前面的指标是"客观测量"，而 AECMOS 是微软开源的一个 AI 模型，用来模拟
"人听起来觉得好不好"，打 1~5 分，越高越好。它给两类分：

  ● Echo（回声分）：回声残留听起来烦不烦。越高说明回声越听不见。
  ● Other（其他/自然度分）：你的声音、整体听感自不自然、有没有被削得发闷。
      越高越自然。
  报告按场景给分：
    - 远单讲 Echo：纯回声段，回声压得干不干净（听感）
    - 近单讲 Other：只有你说话时，你的声音自不自然
    - 双讲 Echo / 双讲 Other：双讲时的回声听感 / 你声音的自然度
    - 挑战赛综合：上面几项的平均分，一个总览分。四种场景齐全时就是"四项
      平均"（微软 AEC 挑战赛口径）；如果这段素材只有部分场景（比如全程纯回声
      只有"远单讲 Echo"一项），综合分就是"现有那几项的平均"，并会在报告里
      标出覆盖了几项（如 1/4）。换句话说：缺场景不会让综合分作废，有几项就
      平均几项；只有一种场景时，综合分就等于那一项。
  全部越高越好。
  提示：不同素材之间比综合分要注意"覆盖项数"是否一致——四项齐全的综合分
  和只有一项的综合分不能直接横比。同一份报告里 A、B 用的是同一段素材、
  覆盖项数相同，所以 A vs B 的综合分对比是有效的。

--------------------------------------------------------------------------------
六、配对对比  —— 直接告诉你"谁赢"
--------------------------------------------------------------------------------
这一节把前面所有指标，按 A1对B1、A2对B2 两两摆好，每一行右边直接标注
"胜:谁"或"≈平"，最后一行给出最关键的一句话：

  ● "-> A1 相对 B1 节省算力 47%"
      意思是：达到同一档次的效果，SeekAudio 的 A1 只用了对手 B1 约一半的
      芯片算力。这是 SeekAudio 方案最核心的卖点——同样的活，省一半的力气。

  怎么读："胜:A1" 就是这一项 A1 更好。注意每个指标"好"的方向不同（有的越
  大越好、有的越小越好），工具已经按正确方向判好胜负，直接看结论即可。

================================================================================
第六部分  怎么快速判断"好不好"（速查表）
================================================================================

  指标                     方向        含义速记
  ---------------------------------------------------------------------------
  CPU 占用率               越低越好    越省芯片
  等效 MHz                 越低越好    越省芯片
  RTF 实时倍率             越高越好    余量越足（必须 >1）
  单帧耗时                 越低越好    只要 < 32000us 就不卡
  片内 SRAM / PSRAM        越低越好    越省内存（片内尤其宝贵）
  栈余量                   越高越好    越安全
  远单讲 ERLE              越高越好    ★消回声能力，最该看
  残余回声 dBFS            越负越好    剩下的回声越安静
  双讲 ERLE                偏低正常    低是"保住你说话"的设计取舍
  链路延时                 越低越好    越不"慢半拍"
  近单讲相关               越接近1越好 你的声音越没被误伤
  双讲相关                 歧义指标    别只看它，参考 AECMOS
  AECMOS 各项 / 综合       越高越好    模拟人耳听感

  一句话看结论：直接翻到"六、配对对比"，看每项"胜:谁"和最后的"节省算力"。

第七部分  常见问题与注意事项
================================================================================

Q1：报告开头的"场景边界"要不要管？
  要看一眼。如果是自动检测[自动]，核对一下三段时间对不对；如果和素材实际
  不符（比如你知道回声在 0-10 秒，但它检测成一堆碎片），就用 --echo/--near
  /--dt 手动指定，结果会更稳。素材结构清晰、你又知道确切时段时，推荐手动。

Q2：自动检测和手动指定，结果会不会差很多？
  结论层面（谁赢谁、省多少算力）通常一致；但绝对数值（尤其远单讲 ERLE）
  可能差几个 dB，因为两者选取的"纯回声帧"范围不同。对结构规整的素材，手动
  分段更贴合真值、数值更稳；自动分段最好当作"独立交叉验证"来用。

Q3：为什么有的节显示"跳过"？
  缺依赖或缺文件。装了 numpy 才有自动分段和音频指标；装了 librosa +
  onnxruntime 且有 .onnx 模型，才有 AECMOS 那一节。只有 log.txt 时，"设备端
  算力/内存"照常输出。

Q4：ERLE 有两套数（主口径 vs 设备端），信哪个？
  以 [主口径] 离线的"远单讲 ERLE"为准（它排除了双讲，最干净）。设备端那套
  是芯片自己算的，因分不清双讲会偏低，只作交叉印证，不作最终结论。

Q5：双讲时 ERLE、双讲相关都不高，是算法差吗？
  不是。双讲时算法要保住你的声音，本就不会把回声压到极致，这是刻意的取舍。
  双讲好不好，应该看 AECMOS 的"双讲 Other"（你声音的自然度）。

Q6：报告存在哪里？
  屏幕会打印一份，同时保存为结果目录下的 aec_report.txt。

Q7：我的素材整段都是回声（或整段双讲、整段近端），怎么测？
  只指定那一类，并加 --no-auto 关掉对其余两类的自动检测，例如整段纯回声：
    python aec_report.py --echo 0:11.22 --no-auto
  如果不加 --no-auto，工具会对你没指定的近端/双讲做自动检测，在单一场景素材
  上会误检出不存在的段，结果就不准。此时报告里那些不存在的场景会显示"-"，
  配对里显示"—"（不可比，而不是打平）。综合分则等于那唯一有分的场景项。
